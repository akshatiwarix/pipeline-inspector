---

## Problem

An open pipeline hides its problems in plain sight. The numbers in a CRM report
— stage, amount, close date — describe where a deal claims to be, not whether
it is actually moving. Three failures repeat across every pipeline review:

**1. "Stalled" is a gut feeling, not a rule.** A rep or manager scanning a
pipeline report calls a deal "stuck" from memory and vibes, not from a
documented threshold. Two managers reviewing the same pipeline flag different
deals, because neither is applying the same rule.

**2. Risk and staleness get conflated.** A deal can be moving right on
schedule and still be risky (one contact, a slipping close date) — or be
stuck in a stage while still looking "engaged" on the surface (frequent
activity, zero progress). Collapsing these into one vague "at risk" label
hides which specific problem a rep needs to act on.

**3. Flags are asserted, never checked against outcomes.** A tool that
says "this deal looks risky" without ever being tested against deals that
actually stalled or actually closed clean is asking for blind trust in the
same way a demo is.

This repo's subject is those three failures: a deterministic pipeline scanner
that applies documented, evidence-linked rules to open opportunities, keeps
"stalled" and "risky" as distinct, separately-evidenced signals rather than
one opaque score, and is checked — automatically, on every run — against a
corpus where the actual underlying health of each deal was fixed at
generation time, so "the flags mean something" is a tested claim.

### What this repo is not

- **Not connected to any other day's code.** Thematically closest to Day 010
  CRM Doctor (data-quality diagnostics) and Day 020 GTM Command Center
  (portfolio-wide triage), and a precursor to later Phase 2 days — fully
  standalone, no shared module, no cross-repo import. Linked from the README
  only.
- **Not a stage-label validator.** Day 030 Stage Validator owns comparing a
  stage *label* against activity for internal contradiction (e.g. "closed-won"
  with no closing activity). This repo never questions whether a stage label
  is honest — it takes the stated stage as given and asks whether the deal is
  moving and healthy within it.
- **Not a lost-deal analyzer.** Day 034 Lost Deal Miner owns finding themes in
  deals that already closed lost. This repo only inspects **open** deals —
  `discovery`, `demo`, `proposal`, `negotiation`. `closed-won` and
  `closed-lost` never appear in the corpus.
- **Not funnel math.** Day 027 Pipeline Calculator owns revenue/conversion
  modeling. This repo never aggregates the pipeline into a forecast number —
  it flags individual opportunities.
- **Not a change-event feed.** Day 039 Pipeline Change Feed owns
  summarizing *changes* to CRM state over time. This repo evaluates a single
  point-in-time snapshot of each opportunity's history, not a stream of
  updates.
- **Not an LLM.** Every flag is a deterministic, rule-based check over
  structured fields and a dated activity log — no model call, no free-form
  generation, no API key, no per-request cost. Same convention as every prior
  day; LLM-based work is reserved for Phase 3 (Day 041+).
- **Not real CRM data.** A committed synthetic corpus of 50 open
  opportunities, generated by a documented, seeded model, each carrying a
  hidden `outcomeProfile` (`healthy` / `stalling` / `at-risk`) the generator
  wrote in but the inspection rules never read. The claim this repo makes —
  that rule-based flags can track genuine risk — is about the *system*, not
  about any real company or deal.
- **Not a CRM.** No write path, no persistence beyond the committed corpus.
  Try It Yourself evaluates pasted text live but never stores it anywhere.

## Intended user

A sales manager or RevOps lead scanning an open pipeline for opportunities
that need attention this week — who wants specific, evidenced reasons a deal
is flagged (not a single opaque risk score), with stalled-but-active deals
kept distinct from actively-deteriorating ones.

Secondary user: an interviewer or engineer reading the repo, who should be
able to see the corpus's generative model, every flag rule, and the
calibration check without running anything.

---

## User journey

1. Land on the **Pipeline Library**. 50 synthetic open opportunities, each
   already scanned by all five rules, are already computed. No upload, no
   sign-up, no config to set.
2. A **pipeline health panel** up top: total opportunities, how many carry
   any flag, how many are `flagged` (critical), and a calibration readout —
   the flag rate broken out by each opportunity's underlying (hidden)
   storyline profile — proving flagged opportunities really do skew toward
   the ones seeded to be unhealthy.
3. **Opportunity table**: every opportunity's company, stage, amount, health
   badge (clear / watch / flagged), and which flags fired. Sortable by
   health or amount; filterable by stage and by flag type.
4. Click an opportunity to open its **detail page**: full activity timeline
   on one side, fired flags on the other — every flag shows its severity,
   the exact activity-log entries it was computed from, and a plain-language
   explanation of the threshold it crossed.
5. Visit **Try It Yourself**: a textarea pre-filled with an example
   opportunity (in a small, documented line format), editable or
   replaceable. The same `inspectOpportunity` function runs client-side and
   shows the flags live — evaluated against **today's real date**, not the
   corpus's fixed analysis date, since this page is a live sandbox rather
   than a graded corpus entry.

## MVP scope

**In:**

- Seeded synthetic corpus: 50 open opportunities, fixed seed, each with
  company/amount/stage/dates, 1-3 contacts, and a dated activity log
  (call / email / meeting / stage-change / close-date-change entries),
  committed to the repo as JSON. Each opportunity carries a hidden
  `outcomeProfile` (`healthy` / `stalling` / `at-risk`) fixed at generation
  time and never read by the inspection rules.
- A deterministic **inspector**: five independent rule functions
  (`checkNoRecentActivity`, `checkStalledInStage`, `checkSingleThreaded`,
  `checkCloseDateSlipping`, `checkHighValueCooling`), each producing zero or
  one `Flag` with its own severity (derived from the signal's own strength)
  and evidence (the exact activity-log entries it fired from).
- A deterministic **health rollup**: `clear` / `watch` / `flagged`, computed
  purely from how many flags fired and at what severity.
- A deterministic **calibration aggregate**: flag rate grouped by the
  corpus's hidden `outcomeProfile`, used both for the pipeline health panel
  and the sweep's calibration invariant.
- Client-safe inspection: the exact same `inspectOpportunity` function that
  powers the precomputed corpus results runs unmodified in the browser for
  the try-it-yourself page, plus a small line-format parser
  (`parseOpportunityText`) for that page's textarea.
- Three screens: **Pipeline Library** (table + health panel), **opportunity
  detail** (timeline + flags + evidence), and **Try It Yourself** (live
  client-side inspection against today's date).
- `GET /api/v1/opportunities`, `GET /api/schema`.
- `npm run sweep`: nine invariants, no network.

**Out (explicitly):**

- Cross-repo integration with any other day's code or data.
- Any live API call, model call, or real CRM/pipeline data.
- Stage-label contradiction checking (Day 030's territory).
- Lost/closed deal analysis — the corpus contains only open deals.
- Funnel/revenue math (Day 027's territory).
- A change-event stream (Day 039's territory).
- Editing or saving an opportunity — no write path, no persistence of
  try-it input.
- A per-opportunity "accuracy" grade against a per-field answer key (there is
  no ground-truth flag list to grade against — the calibration check is a
  corpus-wide statistical claim, not a per-opportunity one).

**A single committed synthetic corpus**, generated by `data/generate.ts` from

## System / architecture

Five layers, dependency arrows pointing only downward.

```
data/                  corpus generation (opportunities + activity logs, seeded RNG)
                        + committed JSON + zod load schema
  ↓
lib/domain/              Opportunity, ActivityEntry, Contact, Evidence, Flag,
                          Inspection, OpportunityResult, PipelineSummary,
                          PipelineInspectionResult — types + zod
  ↓
lib/inspection/           checkNoRecentActivity, checkStalledInStage,
                           checkSingleThreaded, checkCloseDateSlipping,
                           checkHighValueCooling, inspectOpportunity(opportunity,
                           asOfDate), parseOpportunityText — pure, rule-based,
                           severity-assigning functions
  ↓
lib/pipeline-inspector/    orchestration — runs inspectOpportunity across the
                            corpus, assembles OpportunityResult[], aggregates
                            PipelineSummary (flag rate by outcomeProfile)
  ↓
app/                       three screens (library, opportunity detail, try-it)
                            + /api/v1/opportunities + /api/schema
```

### Rules of the architecture

1. **`lib/inspection/` is pure and deterministic.** Same
   `(opportunity, asOfDate)` pair ⇒ byte-identical `Inspection`. No
   `Date.now()` inside the module — the "as of" date is always an explicit
   parameter.
2. **Nothing below `app/` knows about React, HTTP, or the DOM.**
   `inspectOpportunity` must run identically in the browser (Try It
   Yourself) and on the server (precomputed library + API route) — it is the
   same imported function in both places, never reimplemented for either.
3. **The corpus builder always passes the fixed `ANALYSIS_DATE`** as
   `asOfDate`, so the precomputed library and every sweep invariant stay
   deterministic forever. **Try It Yourself always passes today's real
   date** (`new Date()`), because that page is a live sandbox evaluating
   whatever the visitor pastes right now, not a graded corpus entry — this
   is the one place in the app a wall-clock read is correct, exactly the way
   `generatedAt` is a real timestamp in the sibling repos' API routes even
   though their extraction core is pure.
4. **Severity is assigned inside each `check*` function, from the strength
   of that rule's own signal** (days over a threshold, count of pushes) —
   never derived from the corpus's hidden `outcomeProfile`. Severity is a
   claim a rule makes about itself; the calibration check tests that claim
   afterward, corpus-wide. Mixing the two would make severity circular.
5. **`outcomeProfile` is read only by `data/generate.ts` (to construct the
   corpus) and by the calibration aggregate in `lib/pipeline-inspector/`
   (to check the rules against it).** No `check*` function or
   `inspectOpportunity` ever reads it.

## Data model

```ts
type Stage = "discovery" | "demo" | "proposal" | "negotiation"; // open stages only
type OutcomeProfile = "healthy" | "stalling" | "at-risk"; // hidden generator storyline

type ActivityType = "call" | "email" | "meeting" | "stage-change" | "close-date-change";
type ActivityEntry = {
  date: string;             // ISO date, YYYY-MM-DD
  type: ActivityType;
  contactName: string | null; // null for stage-change / close-date-change
  note: string;              // short human-readable description
};

type Contact = { name: string; role: string };

type Opportunity = {
  id: string;
  company: string;
  amount: number;            // whole dollars
  stage: Stage;
  createdDate: string;
  stageEnteredDate: string;  // date the opportunity entered its CURRENT stage
  closeDate: string;         // current expected close date
  outcomeProfile: OutcomeProfile; // generator's hidden storyline tag
  contacts: Contact[];
  activityLog: ActivityEntry[]; // chronological, includes stage-change / close-date-change entries
};

type FlagType =
  | "no-recent-activity" | "stalled-in-stage" | "single-threaded"
  | "close-date-slipping" | "high-value-cooling";
type FlagSeverity = "high" | "medium" | "low";
type Evidence = { activityIndex: number; note: string }; // index into activityLog

type Flag = { type: FlagType; severity: FlagSeverity; detail: string; evidence: Evidence[] };
type HealthLevel = "clear" | "watch" | "flagged";
type Inspection = { flags: Flag[]; health: HealthLevel };

type OpportunityResult = { opportunity: Opportunity; inspection: Inspection };

type PipelineSummary = {
  opportunityCount: number;
  flaggedCount: number;   // health !== "clear"
  criticalCount: number;  // health === "flagged"
  flagRateByOutcomeProfile: { healthy: number; stalling: number; "at-risk": number }; // 0-100
};

type PipelineInspectionResult = {
  generatedAt: string;
  opportunityCount: number;
  opportunities: OpportunityResult[];
  summary: PipelineSummary;
};
```

zod-enforced at every boundary: corpus load, API response.

## Method

### The corpus's generative model

`data/generate.ts` builds 50 opportunities from independently seeded draws:
a company name, a stage (weighted toward earlier stages: discovery 35% /
demo 30% / proposal 20% / negotiation 15%), an amount ($15k–$250k, weighted
so roughly a third clear the $100k "high-value" threshold), 1-3 contacts, and
an `outcomeProfile` drawn `healthy` 40% / `stalling` 30% / `at-risk` 30%.
Dates are all computed backward from a fixed **`ANALYSIS_DATE = "2026-03-01"`**
so the corpus never depends on the real clock. Each profile constructs the
activity log differently so the rules have real signal to find:

- **`healthy`**: recent activity (last touch 0-10 days before analysis date),
  comfortably under its stage's duration benchmark, 2-3 contacts, at most one
  close-date push.
- **`stalling`** (split into two roughly-even subtypes so the two stall
  signals are independently exercised): `stage-bound` opportunities sit well
  past their stage's duration benchmark despite recent activity (busy but not
  progressing); `activity-gap` opportunities have a 15-45 day silence but a
  normal stage duration (quiet but not necessarily behind).
- **`at-risk`** (split into three roughly-even subtypes, one per risk rule):
  `single-threaded` (exactly one contact, everything else normal),
  `slipping` (2-3 `close-date-change` entries in the activity log), and
  `cooling` (amount forced ≥ $100k, stage forced to `proposal`/`negotiation`,
  last activity 7-20 days before analysis date).

This mirrors the sibling repos' ambiguity-flag pattern (Day 021) — profiles
are constructed to deterministically exercise specific rules, so the corpus
has genuine, checkable variety instead of being incidentally uniform.

### The five rules

```
checkNoRecentActivity(opportunity, asOfDate):
  daysSinceLastActivity = asOfDate - max(activityLog date)
  fires when daysSinceLastActivity >= 14
  severity: low [14,21) · medium [21,35) · high >= 35
  evidence: the single most recent activity-log entry

checkStalledInStage(opportunity, asOfDate):
  daysInStage = asOfDate - stageEnteredDate
  benchmark = { discovery: 10, demo: 14, proposal: 21, negotiation: 30 }[stage]
  fires when daysInStage >= benchmark
  severity: low [1x,1.5x) · medium [1.5x,2x) · high >= 2x benchmark
  evidence: the stage-change entry that started the current stage (or the
            opportunity's creation, if the current stage is its first)

checkSingleThreaded(opportunity):
  distinctContacts = count of unique contactName across activityLog entries
                      that have one (call/email/meeting)
  fires when distinctContacts <= 1
  severity: high if (asOfDate - createdDate) >= 30 days, else medium
            (a young single-threaded deal is less alarming than an old one)
  evidence: every activity entry naming that one contact

checkCloseDateSlipping(opportunity):
  pushes = count of "close-date-change" entries in activityLog
  fires when pushes >= 2
  severity: medium if pushes === 2 · high if pushes >= 3
  evidence: every close-date-change entry

checkHighValueCooling(opportunity, asOfDate):
  fires when amount >= 100_000 AND stage in {proposal, negotiation}
            AND daysSinceLastActivity >= 7
  severity: medium [7,14) · high >= 14
  evidence: the single most recent activity-log entry
```

### Health rollup

```
health = "flagged" if any flag.severity === "high" OR flags.length >= 2
       = "watch"   if flags.length === 1 (severity low or medium)
       = "clear"   if flags.length === 0
```

### Calibration

```
flagRateByOutcomeProfile[profile] =
  round(100 * count(opportunities where profile matches AND health !== "clear")
            / count(opportunities where profile matches))
```

## Validation / test plan

**Unit tests** (`vitest`, `lib/**/*.test.ts`, `data/**/*.test.ts`): each
rule against hand-built opportunities with known expected flags/severity;
the health rollup against every flag-count/severity combination; evidence
traceability (every evidence entry's `activityIndex` is valid and points to
an entry consistent with its `note`); `parseOpportunityText` against
well-formed and malformed input; corpus structural assertions (opportunity
count, outcome-profile split, id uniqueness).

**`npm run sweep`** — no network, asserting **nine invariants**:

1. **Corpus size.** Exactly 50 opportunities, unique ids, each with at least
   one contact and one activity-log entry.
2. **Outcome mix.** At least 12 opportunities of each `outcomeProfile`.
3. **Field bounds.** Every `Flag.severity` is one of `high`/`medium`/`low`;
   every `Inspection.health` is one of `clear`/`watch`/`flagged`; every
   `amount` is a positive integer.
4. **Evidence traceability.** Every evidence entry's `activityIndex` is a
   valid index into that opportunity's `activityLog`, and its `note` matches
   that entry's `note`.
5. **Inspection reproducibility.** Recomputing
   `inspectOpportunity(opportunity, ANALYSIS_DATE)` from scratch for every
   opportunity matches the precomputed `OpportunityResult.inspection`
   exactly — no drift between orchestration and the pure rule functions.
6. **Signal coverage.** Each of the five flag types fires at least once
   somewhere in the corpus — proving no rule is dead code.
7. **Risk calibration.** `flagRateByOutcomeProfile["at-risk"]` and
   `flagRateByOutcomeProfile.stalling` are each strictly greater than
   `flagRateByOutcomeProfile.healthy` — proving the flags track genuinely
   unhealthy deals, not noise.
8. **Healthy floor.** `flagRateByOutcomeProfile.healthy <= 25` — most
   deals seeded as healthy pass clean, so the rules aren't trigger-happy.
9. **Determinism.** Running corpus generation and the full inspection
   pipeline twice over the same seed produces byte-identical output
   (`JSON.stringify` equality).

**Manual verification** before shipping: the main journey end to end on the
deployed URL — library loads with the health panel populated and the table
sortable/filterable, an opportunity detail page renders timeline + flags +
evidence for at least one opportunity of each health level, the Try It
Yourself page inspects live from the prefilled example and from a freely
edited replacement with no console errors. Failure states: an opportunity
with zero fired flags renders a clear "no flags" state, not a blank
section; a try-it input with a malformed line renders a clear "line
skipped" notice rather than crashing; an unknown `/opportunities/[id]`
renders a clear not-found state, not a crash.

## Settled decisions

Every one of these was put to the user and confirmed before code was
written, through a structured grilling session.

1. **Standalone repo**, fresh synthetic corpus, zero cross-repo dependency —
   thematically linked to CRM Doctor and GTM Command Center in the README
   only; scoped away from Day 027/030/034/039's future territory.
2. **Domain object is an `Opportunity`**: deal metadata (stage, amount,
   dates) plus a dated activity log — both a snapshot and a timeline, since
   "stalled" and "risky" both need history to reason over.
3. **Scope is open-deal risk flagging only** — no stage-label validation, no
   lost-deal analysis, no funnel math, no change-event feed.
4. **"Stalled" is two independent rule families**: an activity-gap check and
   a per-stage duration-benchmark check, each with its own severity ladder.
5. **"Risky" is three independent rule families**, distinct from stalled:
   single-threaded contact, a slipping close date (2+ pushes), and a
   high-value late-stage deal that's gone quiet — signals stack rather than
   collapsing into one opaque score.
6. **Every flag carries severity (assigned from its own signal's strength)
   and evidence (the exact activity-log entries it fired from)**, matching
   the series' evidence-linked house style — with severity's color direction
   deliberately inverted from the confidence scale used elsewhere in the
   series, since here "high" is bad, not good.
7. **The corpus embeds a hidden `outcomeProfile` per opportunity** (never
   read by the rules), and the app computes a corpus-wide calibration
   readout — flag rate by outcome profile — turning the "identifies risky
   opportunities" claim into a falsifiable, measured one, without requiring
   a per-opportunity ground-truth answer key.
8. **Corpus scale is 50 synthetic opportunities**, mixed roughly 40%
   `healthy` / 30% `stalling` / 30% `at-risk`, each outcome profile split
   into subtypes that individually exercise specific rules.
9. **Two interaction modes**: a browsable precomputed corpus (library +
   detail, matching the series' pattern) plus a "try it yourself" page
   running the identical inspector client-side on user-edited text —
   evaluated against **today's real date**, not the corpus's fixed analysis
   date, since that page is a live sandbox rather than a graded corpus
   entry.
10. Stack, deployment, license, and repo visibility are **identical to the
    sibling repos**: Next.js App Router, TypeScript strict, Tailwind CSS 4,
    zod, vitest/vite-node, zero dependency exceptions, deployed to Vercel,
    pushed to `github.com/akshatiwarix`, MIT license, public repo.
11. **Time limit is one day**, matching the rest of the series.
